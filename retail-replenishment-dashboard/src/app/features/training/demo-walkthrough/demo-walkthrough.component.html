What this walkthrough is really teaching

The console log is only a partial view of the agent's execution. A single visible Anthropic HTTP line appears only after several deterministic stages have already completed for that inventory item.

The most useful skill is therefore not merely reading individual log lines. It is learning how to infer the hidden graph state from:

Number of detected items How many inventory items entered the agent workflow.
Number of Anthropic HTTP calls How many items reached a judgment stage.
Number of monitored orders How many items actually produced replenishment orders.
Shipment appearance timing Whether an order was auto-approved or waited for human approval.

1. The shape of one run

One invocation of: 

python -m agent.main

performs three major phases in sequence.

Phase 1 — Authenticate

1

The Python agent authenticates to Keycloak once using its service-account identity.

It receives the access token used for secured Spring Boot API calls.

Phase 2 — Process Inventory

2

The agent calls: 

GET /inventory/low-stock

Every returned item then traverses the complete LangGraph workflow one item at a time.

Phase 3 — Monitor Delivery

3

Once item processing finishes, the agent remains alive and polls delivery status for created orders.

Monitoring stops after all deliveries complete or the configured monitoring window expires.

Important log-reading lesson:
A visible Anthropic httpx line does not represent the entire processing of one inventory item. It is the visible tail end of a complete graph traversal that already performed several fast backend stages.

2. What happens per item

Every low-stock inventory item goes through the following stages before the next item begins.

recommend_replenishment

3. The branch that matters: auto-approve vs. human review

After supplier availability is checked, the graph selects one of two fundamentally different business paths.

Supplier Found

Order Path

The graph executes: 

recommend_replenishment

The LLM produces the order recommendation and determines whether the recommendation qualifies for auto-approval.

Outcome Result
Auto-approved Order is created as APPROVED and proceeds without human intervention.
Human review required Order is created as RECOMMENDED and waits for manager approval.

No Supplier Found

Escalation Path

The graph executes: 

escalate_shortage

The LLM determines escalation severity:

LOW MEDIUM HIGH CRITICAL

The shortage is escalated for human attention. No replenishment order is created for that item.

The branch is visible in the arithmetic

Detected low-stock items 5
Items reaching judgment 5
Orders monitored 4
Difference 1 escalation

The fifth item reached a judgment stage but never appeared in the delivery watch list because its path produced an escalation rather than a replenishment order.

4. The monitoring loop

After all inventory items have been processed, runner.py moves into delivery monitoring.

Endpoint

Poll Interval

30 seconds

MONITOR_DELIVERY_POLL_SECONDS
Log Behavior

Changes Only

A console line appears only when shipment status changes.

Missing Shipment

404 = Wait

No shipment yet is treated as a normal waiting condition.

What you see What it means
Shipment exists on the first delivery poll The order was already approved and transmitted before monitoring began. In this run, this indicates the auto-approved path.
No shipment appears for several polls The order may still be in RECOMMENDED state waiting for Human-in-the-Loop approval.
Several shipments appear at almost exactly the same time This is consistent with multiple recommended orders being approved together through the dashboard.
No repeated "waiting" log lines Expected behavior. Polling continues silently until the shipment state changes.

6. Cheat sheet: reading your own run's log

Observation Interpretation
Count the httpx lines This tells you how many items reached an LLM judgment stage. If fewer appear than the detected-item count, inspect preceding error lines for an item that failed earlier.
Compare detected count with monitored-order count The difference identifies items that were escalated instead of converted into replenishment orders.
Shipment appears as soon as monitoring starts In this run, the order was auto-approved and transmitted before delivery polling began.
Shipment appears later The order remained in RECOMMENDED state until a human approved it.
Several shipments appear together Strong indication in this walkthrough that multiple orders were approved together through the dashboard.
Silence for an order Not necessarily an error. The monitoring loop may be silently polling while waiting for a shipment to exist.
Need the actual decision detail Open the corresponding run under Agent Runs to inspect stage inputs, outputs, rationale, token usage, and cost.
Need wire-level LLM traffic Use the run's View raw HTTP trace capability for the underlying judgment calls.

Three levels of observability

Console Log

Best for understanding overall execution timing, major transitions, and delivery-state changes.

It intentionally does not expose every internal stage.

Agent Run Detail

Provides the decision-by-decision view behind the condensed console output.

Includes stage inputs, outputs, rationale, token counts, and cost.

Raw HTTP Trace

Provides the lowest-level view of the network traffic behind model judgment calls.

Useful when troubleshooting request or response behavior.

Demo Run Takeaway

A successful agent run is not simply a sequence of LLM calls.

Each visible model request sits inside a larger workflow containing deterministic inventory detection, forecasting, supplier checks, secured API calls, persistent decision logging, order or escalation creation, Human-in-the-Loop approval, asynchronous messaging, and delivery monitoring.

The log becomes much more useful once you learn to read the relationships between counts, timestamps, and shipment state.

The important evidence is not that the AI produced a response — it is that the complete governed business workflow can be reconstructed from authentication through final delivery.
