Three realm roles

Realm roles establish the main authorization personas used by the Spring Boot resource server.

Role Persona Authorized Responsibilities
REPLENISHMENT_AGENT Autonomous Agent Performs the actions required by the automated replenishment workflow, including reads, forecast computation, order creation, shipment operations, escalation creation, and agent-run auditing.
SUPPLY_CHAIN_MANAGER Human-in-the-Loop Approves or cancels recommended orders and acknowledges or resolves escalations requiring human authority.
DASHBOARD_VIEWER Read-Only User Provides read-only access to dashboard information without authority to execute protected business actions.
Important authorization distinction:
Order approval accepts both REPLENISHMENT_AGENT and SUPPLY_CHAIN_MANAGER. The agent can automatically approve critical SKUs under its assigned authority, while a human supply-chain manager approves other recommendations. Escalation resolution remains manager-only.

How authentication works

  1. The user opens the Angular dashboard.
  2. Angular redirects the browser to Keycloak.
  3. The human authenticates to the retail-replenishment realm.
  4. Authorization Code + PKCE protects the authorization-code exchange.
  5. Keycloak returns an access token representing the authenticated user.
  6. Angular sends that token to the Spring Boot API.

  1. The Python agent starts an autonomous or scheduled execution.
  2. It authenticates to Keycloak using client_credentials.
  3. The client identifies itself as retail-replenishment-agent.
  4. Keycloak authenticates the confidential client using its secret.
  5. Keycloak issues an access token representing the client's service account.
  6. The agent sends that JWT to the Spring Boot API when invoking protected operations.

Regardless of which client obtained the token, Spring Boot receives requests using the same HTTP authorization pattern: 

Authorization: Bearer <access_token>

The resource server validates the JWT and uses the role information carried by the token to determine whether the caller is authorized for the requested operation.

Client scopes and token role claims

Client scopes determine which groups of claims are available to clients and ultimately influence what information appears in issued tokens.

Scope Type Purpose
retail-replenishment-roles Custom Contains an explicit realm-role protocol mapper responsible for exposing role information through realm_access.roles.
profile Standard OpenID Connect Standard OIDC profile-related scope.
email Standard OpenID Connect Standard OIDC email-related scope.

The custom scope retail-replenishment-roles contains an explicit realm-role protocol mapper.

That mapper causes the roles associated with the authenticated identity to appear in the token under: 

{
  "realm_access": {
    "roles": [
      "SUPPLY_CHAIN_MANAGER"
    ]
  }
}

This POC exposed an important Keycloak realm-import lesson.

A realm created by importing a partial JSON definition does not necessarily receive the same seeded configuration that the Keycloak Create Realm UI workflow provides.

Standard scopes such as profile and email therefore need to exist correctly in the imported realm if clients are configured to request them.

If a client requests a scope that does not exist in the realm, Keycloak can respond with: 

invalid_scope

The correct fix is not simply to stop requesting the missing scope.

Create the required scope properly, including its appropriate protocol mappers, so that the realm configuration accurately represents the client's security requirements.

Getting the agent token by hand

The Client Credentials Grant is easy to test directly with curl. This is useful when troubleshooting the machine identity independently of the Python agent.

Request a service-account access token

Client Credentials 
# Agent service-account token

curl -X POST \
  http://localhost:8080/realms/retail-replenishment/protocol/openid-connect/token \
  -d grant_type=client_credentials \
  -d client_id=retail-replenishment-agent \
  -d client_secret=<secret from Clients > retail-replenishment-agent > Credentials>
The JSON response contains an access_token. Use that token when calling the Spring Boot API:
Authorization: Bearer <access_token>

Manual token-testing workflow

Step Action What it proves
1 Request token from Keycloak The confidential client and its credentials are configured correctly.
2 Inspect the returned JWT The expected realm role is present in realm_access.roles.
3 Call Spring Boot using Bearer authentication The resource server trusts the Keycloak-issued token.
4 Call an authorized endpoint Role mapping and endpoint authorization are working.
5 Fetch a fresh token when necessary Access tokens are intentionally short-lived rather than permanent credentials.

Short-lived access tokens

Access tokens are short-lived — approximately 15 minutes by default in this POC configuration.

When testing manually, expect to obtain a new token periodically rather than treating an access token as a long-lived API credential.

Security responsibility boundaries

Security Concern Responsible Component Explanation
Human authentication Keycloak Validates the human user's credentials.
Service-account authentication Keycloak Validates the confidential client's credentials.
Access-token issuance Keycloak Issues short-lived JWT access tokens representing the authenticated identity.
Human browser login flow Angular + Keycloak Uses Authorization Code + PKCE.
Machine authentication flow Python Agent + Keycloak Uses the Client Credentials Grant.
JWT validation Spring Boot Operates as the OAuth2 Resource Server and validates incoming access tokens.
Endpoint authorization Spring Boot Enforces the role requirements associated with protected API operations.
Business authorization decision Spring Boot Keycloak supplies identity and roles; the API determines whether those roles permit the requested business operation.

Key IAM design principles

1. One trust anchor

Keycloak remains the central authority for both human and machine identities.

2. Humans and machines are different

Browser users authenticate with Authorization Code + PKCE while headless agents authenticate with Client Credentials.

3. Applications do not handle passwords

Angular, Python, and Spring Boot do not independently implement human credential validation.

4. Roles travel with identity

Realm roles are included in the access token and become inputs to downstream authorization decisions.

5. Authorization stays server-side

Angular may adapt the user experience based on identity, but the Spring Boot API remains responsible for enforcing protected actions.

6. Tokens are temporary

Access tokens are short-lived security artifacts rather than permanent application credentials.

Keycloak architecture takeaway

This POC uses one identity provider to secure two very different types of actors.

A human interacting through Angular authenticates with Authorization Code + PKCE, while the autonomous Python agent authenticates with Client Credentials.

Both ultimately receive short-lived Keycloak access tokens and present those tokens to the same Spring Boot OAuth2 Resource Server.

Keycloak establishes identity and roles; Spring Boot uses that identity to enforce business authorization.
