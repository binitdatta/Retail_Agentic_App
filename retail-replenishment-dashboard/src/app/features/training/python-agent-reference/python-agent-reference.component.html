6. Python LangGraph Agent — Code Reference

Follow the Python agent from the exact command that starts it — python -m agent.main — through configuration loading, Keycloak machine authentication, REST-client construction, LangGraph compilation, per-item state creation, graph execution, Anthropic judgment calls, order or escalation creation, delivery monitoring, auditing, and final process exit.

Python Agent Project Overview
Project

retail-replenishment-agent

This application is the autonomous orchestration layer of the Retail Replenishment POC.

It does not access MySQL directly and does not publish RabbitMQ events directly. Instead, it operates through the secured Spring Boot business API using its own Keycloak service-account identity.

LangGraph coordinates the workflow. Deterministic stages call enterprise APIs, while Anthropic is invoked only for the two stages requiring contextual judgment.

From python -m agent.main to a running LangGraph agent

The Command That Starts Everything 
python -m agent.main

This command contains three important parts.

Part Meaning
python Start the Python interpreter from the current virtual environment.
-m Run a Python module as the application's executable module.
agent.main Locate the agent package and execute main.py as the program entry module.

Why the bottom of main.py matters

Python Entry Point 
if __name__ == "__main__":
    sys.exit(main())

Because agent.main is being executed with -m, Python treats that module as the running program.

The condition becomes true, so: 

main()

is called, and the integer returned by main() is handed to: 

sys.exit(...)

The full execution chain

Step Code What happens
1 python -m agent.main Python executes agent/main.py.
2 main() CLI arguments are parsed.
3 load_settings() Environment variables become one immutable Settings object.
4 run_once(settings, ...) Overall agent orchestration begins.
5 KeycloakTokenProvider(settings) Machine-authentication capability is constructed.
6 ReplenishmentApiClient(...) Secured Spring Boot REST client is constructed.
7 AnthropicJudgment(settings) Bounded LLM judgment capability is constructed.
8 build_graph(...) LangGraph workflow topology is constructed and compiled.
9 api.start_agent_run(...) Persistent audit record for this execution is created.
10 api.get_low_stock(...) Spring Boot returns low-stock items.
11 _item_state_from_dto(...) One API DTO becomes one LangGraph ItemState.
12 graph.invoke(state) The compiled graph actually executes for that item.
13 watch_list Created orders are collected for delivery monitoring.
14 _monitor_deliveries(...) Created orders are polled until terminal delivery state or timeout.
15 complete_agent_run(...) Run status and summary are persisted.
16 return 0 Successful process exits with operating-system exit code 0.

Building the agent versus running the agent

Phase A — Build the Agent

The agent is assembled inside run_once(). 

token_provider = KeycloakTokenProvider(settings)

api = ReplenishmentApiClient(
    settings,
    token_provider
)

anthropic_judge = AnthropicJudgment(settings)

graph = build_graph(
    api,
    anthropic_judge,
    settings,
    dry_run=dry_run
)

At this point the dependencies and graph topology exist, but no low-stock item has yet traversed the graph.

Phase B — Run the Agent

Actual graph execution begins later: 

for item in items:

    state = _item_state_from_dto(
        item,
        agent_run_id,
        dry_run
    )

    result = graph.invoke(state)

graph.invoke(state) is the point where LangGraph begins executing nodes for one inventory item.

Important distinction:
build_graph() defines and compiles the workflow. graph.invoke(state) executes that compiled workflow. Building the graph does not itself detect inventory, call Anthropic, create orders, or create escalations.

main.py — CLI entry point

main.py is intentionally small. Its responsibility is process startup rather than business workflow logic.

Operation What it does
ArgumentParser(...) Defines the agent's command-line interface.
--store-id Restricts the run to one store. Default is all stores.
--dry-run Executes detection, forecasting, supplier checking, and judgment without creating real orders or escalations.
--trigger-type Records whether execution was SCHEDULED, EVENT, or MANUAL.
load_settings() Validates and constructs runtime configuration.
logging.basicConfig(...) Configures log level and output format.
run_once(...) Transfers control into the agent orchestration layer.
return 0 / return 1 Produces a meaningful operating-system exit code for shell scripts, cron, Kubernetes, CI/CD, or schedulers. 

def main() -> int:

    parser = argparse.ArgumentParser(
        description="Retail replenishment LangGraph agent"
    )

    parser.add_argument(
        "--store-id",
        type=int,
        default=None
    )

    parser.add_argument(
        "--dry-run",
        action="store_true"
    )

    parser.add_argument(
        "--trigger-type",
        default="MANUAL",
        choices=["SCHEDULED", "EVENT", "MANUAL"]
    )

    args = parser.parse_args()

    settings = load_settings()

    logging.basicConfig(
        level=getattr(
            logging,
            settings.log_level.upper(),
            logging.INFO
        )
    )

    try:

        run_once(
            settings,
            store_id=args.store_id,
            dry_run=args.dry_run,
            trigger_type=args.trigger_type
        )

        return 0

    except Exception:

        logging.exception("Agent run failed")

        return 1


if __name__ == "__main__":
    sys.exit(main())

config.py — runtime settings

Configuration is loaded before any agent dependency is created. This keeps credentials, URLs, model selection, and timing parameters outside the business code.

Name Responsibility
_env(name, default, required) Reads one environment variable and fails immediately when a required value is absent.
Settings Frozen dataclass containing API, Keycloak, Anthropic, forecasting, monitoring, and logging configuration.
load_settings() Creates the immutable Settings instance used by every downstream component.

Required secrets fail early

Two environment values are explicitly required: 

KEYCLOAK_CLIENT_SECRET
ANTHROPIC_API_KEY

If either is missing, startup fails before the agent creates an execution record or begins processing inventory.

runner.py — assembling the agent

The first lines of run_once() behave like a small, explicit dependency-injection container.

Object Depends On Provides
KeycloakTokenProvider Settings OAuth2 machine access token.
ReplenishmentApiClient Settings + token provider Authenticated access to Spring Boot.
AnthropicJudgment Settings Bounded judgment calls plus token/cost/HTTP trace.

auth.py — Keycloak machine identity

No human user participates in the agent's authentication flow. The Python process authenticates as the confidential retail-replenishment-agent client.

get_token()

Every REST call eventually requests a token through: 

token_provider.get_token()

If the cached token is still valid, it is reused. Otherwise a new access token is fetched.

_fetch_token()

Sends the OAuth2 grant: 

grant_type=client_credentials

Token expiry is intentionally shortened internally by 30 seconds so the agent does not attempt an API call using a token at the exact edge of expiration.

api_client.py — secured Spring Boot client

The graph does not construct HTTP requests directly. All calls pass through ReplenishmentApiClient.

The central _request() method

Every public API-client method eventually reaches: 

headers["Authorization"] =
    "Bearer " + token_provider.get_token()

response = session.request(...)

This ensures every business API request carries a current Keycloak access token.

Method Backend Capability
get_low_stock() GET /inventory/low-stock
get_product() GET /products/{id}
compute_forecast() POST /demand-forecasts
get_supplier_availability() GET /suppliers/availability
create_replenishment_order() POST /replenishment-orders
get_delivery_status() GET /replenishment-orders/{id}/delivery-status
create_escalation() POST /escalations
start_agent_run() POST /agent-runs
complete_agent_run() PATCH /agent-runs/{id}
log_decision() Persists one graph-stage decision.
log_llm_call() Persists logical model request/response, usage, and cost.
log_llm_http_trace() Persists redacted raw HTTP request/response details.

Why only GET requests are automatically retried

The requests session configures retries for: 

allowed_methods=["GET"]

That is deliberate.

Repeating an idempotent GET is generally safe. Automatically retrying an uncertain POST could create a duplicate order, escalation, decision log, or agent-run record.

llm_clients.py — bounded Anthropic integration

This is the only module that directly communicates with Anthropic.

Function / Class Responsibility
_redact_headers() Fully replaces credential-bearing headers such as x-api-key and authorization with REDACTED.
_safe_json() Attempts JSON parsing but preserves raw text when the body is not valid JSON.
HttpTrace Represents raw HTTP request and response evidence.
LlmCallResult Normalized result used by graph nodes regardless of whether the model call succeeded or failed.
_estimate_cost() Calculates estimated usage cost from configured per-token pricing.
AnthropicJudgment.complete_json() Makes the Anthropic request, measures latency, captures token usage, estimates cost, collects raw HTTP trace data, and returns one normalized result object.
parse_json_response() Safely converts model text into a Python dictionary and falls back to a controlled result when parsing fails.

Why with_raw_response is used

Instead of calling only the normal SDK method, the client calls: 

messages.with_raw_response.create(...)

This makes the underlying HTTP request and response available, allowing the POC to persist evidence such as:

HTTP method Actual method sent
Request URL Actual endpoint
Request headers Sensitive values redacted first
Request body Actual serialized payload
Status code Actual HTTP response status
Response headers/body Actual response evidence

Why make_*_node() factories exist

LangGraph expects each node to behave approximately like: 

state -> partial_state

But the node also needs dependencies such as:

API client Anthropic client Forecast settings Dry-run policy

The factory captures those dependencies in a Python closure and returns the simpler callable that LangGraph invokes later.

nodes.py — what executes inside the graph

Node / Router Type Behavior
detect_low_inventory Deterministic Records the already-detected inventory deficit as an auditable decision.
forecast_demand Deterministic Calls Spring Boot to calculate demand forecast and stores the result in state.
check_supplier_availability Deterministic Retrieves eligible suppliers and stores them in state.
route_after_supplier_check Router Supplier exists → recommendation. No supplier → escalation.
recommend_replenishment LLM judgment Uses deficit, forecast, criticality, and supplier data to decide CREATE_ORDER/HOLD, quantity, auto-approval, and rationale.
route_after_recommend Router Order exists → monitor stage. No order → END.
monitor_delivery Deterministic Per-item graph node records that the order was submitted and added to the run's watch list.
escalate_shortage LLM judgment Uses criticality, deficit, and optional shelf-life context to assign escalation severity.

graph.invoke() — the point where the agent really runs

Per-Item Execution

After low-stock inventory is fetched, the runner executes: 

for item in items:

    state = _item_state_from_dto(
        item,
        agent_run_id,
        dry_run
    )

    result = graph.invoke(state)

Every call to: 

graph.invoke(state)

means one independent low-stock item traverses the compiled LangGraph workflow from its entry node until one END condition is reached.

If five low-stock items are returned, the runner invokes the compiled graph five times.

One failed item does not kill the entire run

graph.invoke(state) is wrapped in an item-level exception handler. 

try:

    result = graph.invoke(state)

except Exception as exc:

    logger.exception(
        "Item %s / %s failed",
        item["storeCode"],
        item["skuCode"]
    )

    errors.append(...)

    continue

A single malformed item, API error, or unexpected graph-stage exception is recorded, but processing continues with the next low-stock item.

How orders leave the graph and enter delivery monitoring

After each invocation, runner.py examines the graph result.

Graph Result Runner Action
order exists Increment order count and add the order to watch_list.
order status is APPROVED Increment auto-approved order count.
escalation exists Increment escalation count.
neither exists Nothing is added to delivery monitoring.

_monitor_deliveries() — the post-graph monitoring loop

The per-item monitor_delivery graph node does not wait minutes for a shipment. Long-running wall-clock monitoring is kept outside the graph.

Configurable

MONITOR_DELIVERY_POLL_SECONDS
Max Duration

Configurable

MONITOR_DELIVERY_MAX_MINUTES
Normal 404

Keep Waiting

Shipment may not exist yet.

Terminal States

DELIVERED / EXCEPTION

Step Monitoring Behavior
1 Calculate monitoring deadline.
2 Iterate through all watched replenishment orders.
3 Call get_delivery_status(order_id).
4 Treat HTTP 404 as "shipment not created yet."
5 Compare current shipment status with last observed status.
6 Persist a decision only when status changes.
7 End early when every shipment reaches a terminal status.
8 Otherwise sleep for the configured polling interval.

Completing the agent run

Once all inventory items and monitored deliveries have been processed, runner.py builds a human-readable summary. 

Scanned N low-stock item(s).
X order(s) recommended.
Y auto-approved.
Z shortage escalation(s) raised.

The run is then closed through: 

api.complete_agent_run(
    agent_run_id,
    status="COMPLETED",
    summary=summary
)

This prevents the agent-run table from containing a run that remains indefinitely in RUNNING state after normal completion.

What if the overall run crashes?

run_once() also has an outer exception handler.

Before re-raising the failure, it attempts: 

api.complete_agent_run(
    agent_run_id,
    status="FAILED",
    summary="Run failed: ..."
)

The error then propagates back to main(), which logs the failure and returns exit code 1.

What changes with --dry-run?

python -m agent.main --dry-run

The graph is still built and invoked normally.

Detection, forecasting, supplier lookup, LLM judgment, decision logging, LLM-call logging, and HTTP-trace capture can still execute.

But the judgment nodes stop before performing the final transactional business write:

Normal Run Dry Run
Create replenishment order Log what would have been created
Create shortage escalation Log what would have been escalated
Monitor resulting deliveries No real created order to monitor

Key Python agent design principles

1. Build once, invoke many times

One compiled graph is created for the run and then invoked independently for each low-stock item.

2. One state per inventory item

Each SKU/store condition receives its own ItemState and traverses the graph independently.

3. LLM use is bounded

Anthropic is invoked only for recommendation and escalation judgment.

4. Business writes go through the API

Python never bypasses Spring Boot to manipulate MySQL directly.

5. Auditability is part of execution

Every deterministic stage and every LLM judgment produces persisted audit evidence.

6. Wall-clock waiting stays outside the graph

Long delivery polling remains in runner.py instead of making every graph invocation sleep for minutes.

The most important concept to understand

The command: 

python -m agent.main

does not directly "run LangGraph."

It first starts the Python application, loads configuration, constructs security and integration dependencies, creates the Anthropic client, builds and compiles the LangGraph workflow, creates an auditable agent-run record, retrieves the current workload, and only then invokes the compiled graph.

The graph is the per-item decision engine; runner.py is the overall business-process orchestrator.

Python Agent Architecture Takeaway

The Python application deliberately separates process startup, orchestration, graph topology, business-stage implementation, REST integration, authentication, configuration, state, and LLM integration.

That separation makes the agent easier to understand and prevents the LLM from becoming the application architecture itself.

main.py starts the process. runner.py assembles and governs the run. graph.py constructs the decision workflow. nodes.py performs each stage. api_client.py reaches the enterprise system. auth.py establishes machine identity. llm_clients.py provides bounded AI judgment.

Python and LangGraph orchestrate the work; Keycloak establishes machine identity; Spring Boot enforces business authority; MySQL remains the system of record; RabbitMQ executes asynchronous side effects; Anthropic supplies only the judgment that deterministic software cannot reasonably provide.
