Database ownership model

The schema is DBA-owned and intentionally managed independently from the Spring Boot JPA entity model.

Tables, indexes, constraints, generated columns, views, foreign keys, and reference structures are written explicitly as versioned SQL rather than being created automatically from Java entities.

Spring Boot runs with: ddl-auto: validate
Hibernate verifies that the database schema matches the entity mappings during application startup. If the database and Java model drift apart, the application fails fast rather than modifying the production schema automatically.

Design choices worth remembering

Several database decisions in this POC are intentional safeguards against concurrency errors, data drift, and accidental loss of historical records.

A version column is maintained on:

Table Why concurrent modification matters
store_inventory POS-driven inventory activity and autonomous agent activity may attempt to modify the same inventory state.
replenishment_order Multiple workflows may interact with the lifecycle of the same replenishment order.

Optimistic locking allows the application to detect that the row changed between read and update rather than silently overwriting a newer version.

line_total on replenishment_order_line is calculated by MySQL as a generated column rather than being independently calculated and persisted by Java. 

line_total = ordered_qty × unit_cost

This gives the calculation one authoritative implementation and removes another opportunity for application-calculated values to drift from persisted data.

Relationship Type Behavior Reason
Master data No cascading delete A store or product cannot disappear while transactional history still references it.
Aggregate child records Cascade with parent Records such as order lines, tracking events, and decision logs belong to their parent aggregate.

Hibernate schema validation

Why use ddl-auto: validate?

The application receives the safety benefit of Hibernate checking its mappings against the physical schema without allowing Hibernate to become the schema-management authority.

A mapping mismatch therefore becomes a startup failure instead of an unnoticed runtime discrepancy.

Schema ownership boundary

Concern Owner
DDL definition Versioned SQL / DBA
Tables and indexes Database schema
Foreign-key strategy Database schema
Java object mapping JPA / Hibernate
Schema compatibility check Hibernate validation
Automatic schema mutation Disabled

Common Hibernate / MySQL type mismatches

Two mappings discovered while building the POC demonstrate why schema validation is useful. The Java type alone did not cause Hibernate to infer the exact database type required by the hand-written MySQL schema.

A plain Java String normally maps as a VARCHAR, but the physical schema defines run_uuid as CHAR(36). 

// CHAR(36) — plain String defaults to VARCHAR in Hibernate

@Column(
    name = "run_uuid",
    length = 36,
    columnDefinition = "CHAR(36)"
)
private String runUuid;

A plain Java Integer does not describe the precise MySQL column definition required by the schema. 

// SMALLINT UNSIGNED — plain Integer defaults to INTEGER

@Column(
    name = "http_status_code",
    columnDefinition = "SMALLINT UNSIGNED"
)
private Integer httpStatusCode;

What happens when the mapping is wrong?

These mismatches were discovered because Hibernate validated the entity model during Spring Boot startup. 

SchemaManagementException

That failure is desirable in this architecture. It exposes schema drift immediately rather than allowing the application to start with an incorrect assumption about the database.

Key database lessons from this POC

Principle Implementation in this POC
Schema ownership is explicit SQL defines the physical model; JPA maps to it.
Schema drift fails fast ddl-auto: validate checks entity/schema compatibility at startup.
Reference domains are data Status values are normalized into reference tables instead of being embedded as MySQL ENUM definitions.
Concurrency is expected Version columns protect important mutable aggregates through optimistic locking.
Auditability is persistent Agent decisions and LLM calls are stored as durable business observability records.
Derived data has one owner MySQL calculates line_total as a generated column.
Historical integrity is protected Master-data deletes do not cascade through existing transactional history.
Database architecture takeaway

MySQL is not simply persistence behind the AI agent. It is the durable system of record for the business application.

Agent reasoning can recommend actions, but inventory state, replenishment orders, escalations, delivery tracking, execution history, and LLM observability are persisted independently of any individual model invocation.

The database schema remains deterministic, versioned, auditable, and independently governed while the AI layer remains replaceable.
