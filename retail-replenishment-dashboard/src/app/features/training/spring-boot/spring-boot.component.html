Package Responsibility Design Intent

exception/ Error handling Global exception handling produces a consistent ErrorResponse JSON structure.
messaging/ Asynchronous integration RabbitMQ event publisher and event listeners.

Why open-in-view: false matters

The application deliberately disables Hibernate Open Session in View: 

spring:
  jpa:
    open-in-view: false

Controller serialization cannot accidentally trigger lazy database queries after the service transaction has ended.

If a controller needs related data, the service/repository query must retrieve that data explicitly, including JOIN FETCH where appropriate.

Entities & repositories

Every entity maps to the DBA-controlled DDL rather than defining the physical schema itself. Hibernate validates the mappings at startup through ddl-auto: validate.

Status fields map to reference-table entities through @ManyToOne relationships rather than Java enums.

That mirrors the normalized database model and means a new database status can be introduced without requiring a Java enum change and application rebuild.

Several audit and AI-observability fields are stored as MySQL JSON columns:

Table JSON fields
agent_decision_log input_snapshot
output_decision
llm_call_log request_payload
response_payload

Hibernate maps the column explicitly: 

@JdbcTypeCode(SqlTypes.JSON)
private String requestPayload;

At the DTO boundary, a small JsonUtil helper exposes the stored value as actual nested JSON rather than returning an escaped JSON string.

Low-stock detection is implemented as one JPQL query in StoreInventoryRepository.

The query mirrors the database view logic: 

(on_hand_qty - allocated_qty) <= reorder_point

Keeping the rule centralized prevents slightly different versions of low-stock logic from being duplicated throughout controllers, services, and agent code.

KeycloakRealmRoleConverter

Keycloak places realm roles in: 

realm_access.roles

The custom converter extracts those nested roles and turns them into Spring Security authorities.

RestAuthenticationEntryPoint

Handles authentication failures generated before the request reaches a controller.

HTTP 401 responses therefore still use the application's standard ErrorResponse structure.

RestAccessDeniedHandler

Handles authenticated callers who do not have sufficient authority for a protected operation.

HTTP 403 responses use the same predictable JSON error contract as application-layer failures.

Why special 401 / 403 handling is necessary

Spring Security's filter chain executes before the request reaches the Spring MVC controller layer.

That means authentication and authorization failures cannot rely exclusively on normal controller exception handling.

Result: authentication errors, authorization errors, validation errors, and business exceptions can all return the same predictable ErrorResponse JSON shape.

RabbitMQ messaging

The application uses the topic exchange retail.replenishment.events. Four routing keys define the asynchronous integration points used by the current POC and future event-driven extensions.

Routing Key Consumer Responsibility
replenishment.order.created SupplierIntegrationStubListener Stands in for an external supplier integration. It transmits an approved order, creates a shipment, and hands the shipment to the delivery simulator. A still-RECOMMENDED order is left alone.
delivery.status.updated DeliveryStatusAuditListener Serves as a delivery-status log sink and provides a natural integration point for future live dashboard updates.
shortage.escalated ShortageEscalationNotificationListener Provides a severity-prefixed notification stub representing future Slack, email, or enterprise-notification integration.
inventory.low-stock.detected LowStockDetectedListener Nothing publishes this event yet. It intentionally provides the hook for evolving from scheduled polling toward an event-driven agent trigger.

Synchronous Work

REST requests perform the immediate business operation, enforce security, validate state, and commit authoritative data to MySQL.

Asynchronous Side Effects

RabbitMQ decouples secondary activities such as supplier integration, shipment simulation, delivery-event auditing, and notifications from the original REST request.

The transaction / messaging race condition

A real concurrency bug discovered while building the POC

EventPublisher.publish() originally sent the RabbitMQ message immediately from inside an @Transactional service method.

That created a race:

Sequence What happened
1 Service changes the order state inside a database transaction.
2 Event is immediately published to RabbitMQ.
3 Fast consumer receives the event.
4 Consumer queries MySQL before the producer transaction commits.
5 Consumer sees the previous database state.
Observed symptom:
An order was approved, but the RabbitMQ consumer immediately logged that the order was still awaiting approval.

Fix: publish only after transaction commit

EventPublisher 
if (TransactionSynchronizationManager.isSynchronizationActive()) {

    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {

            @Override
            public void afterCommit() {
                doPublish(routingKey, payload);
            }

        }
    );

} else {

    doPublish(routingKey, payload);

}
Why this works:
The RabbitMQ message is not published until the relational transaction has successfully committed. A consumer receiving the event can therefore read the state represented by that event.

Correct transaction and event ordering

Step Action Reason
1 Validate request Reject invalid or unauthorized work before modifying state.
2 Execute business rule Determine the correct deterministic business outcome.
3 Persist MySQL state Prepare the authoritative database changes.
4 Commit transaction Make the business state durable and visible.
5 Publish RabbitMQ event Announce a state transition that actually exists durably.
6 Consumer reacts Downstream processing can now query consistent state.

Why this lesson matters beyond the POC

This race condition is not specific to Spring Boot, RabbitMQ, retail replenishment, or Agentic AI.

It is a general distributed-systems problem whenever a relational database transaction and an external message broker participate in the same business workflow.

An event should not claim that durable business state exists before that state has actually committed.

Spring Boot responsibility matrix

Concern Primary Spring Component Responsibility
HTTP API Controllers Receive REST requests and expose stable API contracts.
JWT validation Spring Security Validate Keycloak-issued access tokens.
Authorization SecurityConfig Enforce realm-role requirements for protected operations.
Business logic Services Execute deterministic business rules and transaction boundaries.
Persistence Repositories / Hibernate Query and update the MySQL system of record.
API representation DTOs / Mappers Prevent persistence entities from becoming external API contracts.
Input validation Bean Validation Validate request DTO constraints before business processing.
Error consistency Exception package Produce standardized ErrorResponse objects.
Async integration Spring AMQP Publish and consume RabbitMQ business events.

Key Spring Boot design principles

1. Controllers stay thin

HTTP concerns remain separate from business rules and transaction management.

2. Services own business logic

Services define the authoritative behavior and control transactional boundaries.

3. Entities stay internal

DTOs protect the REST contract from persistence-model implementation details.

4. Database ownership stays explicit

Hibernate validates the schema but does not become the DDL-management authority.

5. Security stays server-side

Every protected business operation is authorized by the API, regardless of what the Angular client displays.

6. Events follow durable state

RabbitMQ messages are published after the relevant relational transaction has successfully committed.

Spring Boot architecture takeaway

The Spring Boot application is intentionally more than a collection of REST endpoints.

It is the deterministic enterprise boundary around the AI agent: authentication is validated here, authorization is enforced here, business rules execute here, transactional state is committed here, and asynchronous events originate here.

The Python agent can reason, plan, and orchestrate, but it does not bypass this layer to manipulate MySQL or RabbitMQ directly.

The agent proposes and orchestrates work; Spring Boot remains the secure, transactional business system that performs it.
