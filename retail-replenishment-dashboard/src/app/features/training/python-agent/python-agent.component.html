6. Python agent

Not Flask — there's no web framework here at all. It's a plain Python CLI (python -m agent.main) built on LangGraph, calling the Spring Boot API as a client. It runs to completion and exits, rather than serving HTTP requests.

Project: retail-replenishment-agent. LangGraph, requests, python-dotenv, the Anthropic SDK.

Overview

agent/
  config.py     Settings loaded from .env — no hardcoded credentials anywhere else
  auth.py       Keycloak client_credentials token fetch, auto-refresh near expiry
  api_client.py One method per backend endpoint. GET-only retries — a retried
                POST could double-create an order
  llm_clients.py Anthropic wrapper, returns a uniform LlmCallResult for audit logging
  state.py      LangGraph state — one ItemState per low-stock item
  nodes.py      The six pipeline stages
  graph.py      Wires the stages into a LangGraph StateGraph
  runner.py     Orchestrates one full run: fan out over every item, then watch
                delivery on whatever orders it created
  main.py       CLI entrypoint: --store-id, --dry-run, --trigger-type
python -m agent.main --dry-run   # exercises everything, creates nothing
python -m agent.main             # the real thing

LangGraph pipeline

detect_low_inventory -> forecast_demand -> check_supplier_availability
    --(supplier found)-->    recommend_replenishment --(order created)--> monitor_delivery -> END
                                                       --(no order)------> END
    --(no supplier)----->    escalate_shortage -> END

detect, forecast, check_supplier, and monitor are deterministic — arithmetic and lookups, no LLM call, logged with no llm_model. The runner fans this graph out over every item GET /inventory/low-stock returns, then stays alive afterward polling delivery status on whatever orders got created — for up to MONITOR_DELIVERY_MAX_MINUTES (default 8, deliberately longer than the backend simulator's ~6 minute cadence).

LLM judgment calls

Both judgment stages run on Anthropic (this POC deliberately uses one provider, not a multi-provider split):

  • recommend_replenishment — given the deficit, forecast, and best available supplier, decides whether to order, how much, and whether it qualifies for auto-approval. Auto-approval logic lives in the prompt: critical SKU + reliable low-lead-time supplier → skip human review.
  • escalate_shortage — given the deficit and (when available) the SKU's shelf life, decides severity: LOW / MEDIUM / HIGH / CRITICAL.

Both are instructed to return strict JSON and both are parsed defensively — parse_json_response() falls back to a safe default and keeps the raw text for the audit trail rather than crashing the run on one malformed reply. Every call logs a full llm_call_log row: request/response payload, token counts, latency, estimated cost.
